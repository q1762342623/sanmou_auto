# 排行榜（排行）抓包实测 · 技术参考

目标：点「排行」→ 逐个榜单切换，用设备内 tcpdump 确认**每个榜单的数据到底在哪个 RPC/哪一帧**。

工具：[`scripts/probe.py`](../scripts/probe.py)（抓包 + 解码）、
[`scripts/report.py`](../scripts/report.py)（HTML 报表）、
[`scripts/collect.py`](../scripts/collect.py)（采集编排 + 人数校验）

```bash
python scripts/probe.py                    # 抓包 + 逐榜单点击 + 解析
python scripts/probe.py --cold --scroll 1  # 先冷启动（清榜单缓存）再抓
python scripts/probe.py --no-capture        # 只解析最近一批 pcap
python scripts/probe.py  --analyze <pcap>   # 只解析指定 pcap
```

## 2. 抓包要点（踩过的坑）

1. **一段包 = 一个榜单**。解码链会把整条 TCP 流合并成一个 chunk，所有帧共用
   chunk 的**第一个包时间戳**（实测 66 帧同一时刻），按时间窗归属完全失效。
2. **XOR key 每次连接随机**，同一局内全窗口共用。单段帧太少时本地推导会挑错 key
   （解出中文全是乱码），必须**先合并所有段的帧求一把全局 key**。
3. 榜单响应可能点击后 3~4s 才到：窗口结束前多等 1.2s，响应过小（<1.5KB）再点一次。
4. **阵营榜有客户端缓存**：同一会话内反复切页签不会重新请求；
   冷启动那次也抓不到（数值疑似登录期下发）。冷启动只清掉了「个人/同盟」的缓存。
5. 全端口对照（`tcp` 不过滤）确认：切「阵营」页只有 `75B` 上行 / `360B` 下行，
   没有大响应 → 数据确实来自客户端缓存，不是漏抓端口。

## 3. 协议结论

- 服务端 → 客户端，游戏端口 `20010`。
- 帧结构：2 字节长度 → 9 字节传输头 → XOR → **2 字节 RPC 前缀（opcode）** → 对象。
- 排行榜数据主要走 **opcode `58624`**（十进制）；页签/开关类小包是 `9989`、`7941`。
- `58624` 单帧约 9KB ≈ 50 行，一个榜单会连发多帧（个人榜总量约 300~590 行）。
- 行布局（实测）：

  ```
  02 00 00 00 04 00 00 00 | u32 分数 | u32 州/阵营ID | u32 等级 | u32 名次
  ... 05 00 00 00 ... | "unionName\0" <联盟名> "\0"
      | "unionId\0" | "coord\0" | "roleId\0" | "bornStateId\0"
  ```

  典型样本（个人繁荣榜）：`164805 / 148 / 86 / 乱丨稷下学宫`（与 UI 第 1 行一致）。
  个人武勋榜同结构，分数为武勋值（样本 `7509835`）。
- 阵营榜行结构不同：`[城池数量, 积分/名额, 阵营ID, 名次]`，
  样本 `24 / 5350`、`24 / 135`（霸业名额）、`23 / 75`。
- **玩家名不在 `58624` 里**：该 RPC 只带 `roleId`，玩家名由另外的名字缓存 RPC 下发。

## 6. 「300 个」到底是多少行 / 要不要拖到底

实测结论：**不用拖到底，第一次请求就已经下发 300 行**。

- 榜单行在帧里是**一个 sproto 数组字段**，每页固定 **50 项**（项内 ints = `[分数, 名次, 名次]`）。
  `scan_rows()` 用数组解析 → **每帧正好 50 行**，6×50 = 300；首占榜 2×50 = 100。
- 老口径 `scan_records()`（按行标记 `02 00 00 00 04 00 00 00` 切行）会漏 1~2 行/帧：
  个别行的分数/名次字段被省略（编码变体，起手是 `01 00 00 00 02 00 00 00 03 00 00 00`），
  所以 300 人的榜只能切出 293~295 行、首占榜 97 行。**做人数校验不要用 scan_records。**
- UI 一直往下拖会重复请求同一批 → 帧数暴涨（349→540 帧）、pcap 变大（100KB→240KB），
  但**唯一行数不再增加**，拖到第 36 屏恰好停在第 300 名（`镜|疯疯 149265`），再拖回顶。
- 之前「数量对不上」是统计口径问题：300 行里有大量同分（如 149350 出现两次），
  按「唯一分数」只有 121 个。正确口径是**行数**，见 `tools/_rank_count.py`、`tools/_rank_frame_rows.py`。
- 下拉必须从列表内部起手（`y≈1000`）；从 `y≈1150` 起手会落在固定的「未入榜」行上，列表根本不滚。

### 各榜单固定条数（重要，别按帧数硬算）

| 榜单 | 每份数据 | 帧结构 |
| --- | --- | --- |
| 个人繁荣榜 / 个人武勋榜 | **300 人** | 6 帧 × 约 50 行 |
| 个人首占榜 | **100 人/等级** | 2 帧 × 约 50 行（`49~50`） |
| 阵营内排行 | 每个阵营一份全量 | 多个 9KB 帧 |


补充：首占榜的数值列是「占领时间」，行里的 u32 是**时间戳**（如 `1794293474`），
不是分数；`scan_records()` 会把时间戳读成 `score`，用它判断行数可以，判断分数不行。
另外，同一个 pcap 段里常混有「点页签时默认加载的繁荣榜 6 帧」，需要按帧尺寸
（约 9KB = 排行榜行帧，约 11KB = 首占榜行帧）或按首行数值区间区分。

## 7. 静态 HTML 报表（本功能的输出）

```bash
python scripts/report.py                      # 最新批次
python scripts/report.py --batch 20261126_000834 --level 9
```

输出：`screenshots/flow/rank_probe/rank_report_<批次>.html` 与 `rank_report_latest.html`
（单文件、无外部依赖，双击即可看）。

| 区块 | 内容 |
| --- | --- |
| 个人繁荣榜 | 按同盟汇聚：上榜人数 / 繁荣度合计 / 平均 / 最高 / 最低，按合计降序 |
| 个人武勋榜 | 同上（武勋值） |
| 个人首占榜（9 级） | **只做分类**：同盟 / 上榜人数 / 占比；表格上方单独标「**最后一位（第 100 名）占领时间**」 |
| 阵营 | **每个阵营一张表**：填「问鼎人数 X」「紧接的霸业人数 Y」；表内逐盟给出 问鼎人数 / 问鼎占比 / 霸业人数 / 霸业占比 / 问鼎+霸业 / 合计占比（无「未获得」列）；输入存 localStorage |

阵营区口径（2026-11-26 最终版）：

- 名额按**名次区间**分配（不是按占比分摊）：前 X 名得问鼎，
  紧接着的 Y 名（第 X+1 ~ X+Y 名）得霸业，其余未获得；
  X、Y 都是**人数**（不是截止名次），超界会自动裁剪（X ≤ 总数、Y ≤ 总数−X）；
- 名次来源：阵营内排行每行一个 `unionName`，按「帧顺序 + 帧内顺序」拼成有序序列
  （一段约 550 行），序列下标即名次；
- 每张表列：同盟、问鼎人数、问鼎占比（该盟问鼎 ÷ X）、霸业人数、
  霸业占比（该盟霸业 ÷ Y）、问鼎+霸业、合计占比（该盟问鼎+霸业 ÷ (X+Y)，**都在本阵营内算**）；
- 顶部提示「问鼎 x 人 · 霸业 y 人（阵营共 N 人）」，X、Y 自动裁剪到 [0, N]；
- **抓包时「先切另一阵营」必须放在窗口外**：否则同一段 pcap 里会同时有两个阵营的数据，
  统计时同盟互相污染（实测太平道段曾出现与讨逆军一模一样的 202/175/172）。
  修正后：讨逆军 = 乱丨稷下学宫/北辰/极夜（550 人），太平道 = 云台阁/沧溟/藏丨剑阁（549 人）。

实现要点：
- 数据直接重新解析 pcap（不走 `rank_frames.jsonl`，那个里每帧只留 20 行，会丢数据）；
- 分类靠文件名 + 数值区间：繁荣度 `< 1e6`、武勋 `1e6~1.6e9`、首占榜是 `>= 1.6e9` 的时间戳；
- 按 `(分数, 州, 等级, 同盟)` 去重，避免同批重复帧重复计数；
- 页面顶部会打印「行数 / 同盟数」，方便核对是否抓全（繁荣/武勋 ~300 行，首占 9 级 ~100 行）。

抓干净数据的一轮：

```bash
python scripts/probe.py --only 个人繁荣榜,个人武勋榜,个人首占榜 --firstocc9 --extra
python scripts/report.py
```

> 抓包细节（2026-11-26 修）：页签点击要放在**起抓之前**（否则会混入默认榜），
> 且目标榜若是「已选中的默认榜」，要先点同页签的兄弟榜再点回来，否则服务端不重发；
> 首占榜则把「点开榜单」放窗口外、窗口内只切 9 级，这样一段包就是纯 100 行。

## 8. 采集编排：人数硬校验 + 自动重抓

```bash
python scripts/collect.py            # 抓 → 校验 → 不达标重抓该榜 → 生成 HTML
python scripts/collect.py --tries 4  # 单榜最多重抓 4 次
```

| 榜单 | 期望（**完整人数，不用宽松阈值**） | 说明 |
| --- | --- | --- |
| 个人繁荣榜 | **300 行** | 6 帧 × 50 行；行数来自 `scan_rows()` 数组解析，是精确值 |
| 个人武勋榜 | **300 行**；**< 50 行视为正常** | 赛季初期武勋榜可能只有 0~几十人，不触发重抓；≥50 但 < 300 才重抓 |
| 个人首占榜（9 级） | **100 行** | 2 帧 × 50 行 |
| 阵营内排行 | 每阵营 ≥ 100 人，且两阵营同盟集合**无交集** | 有交集即判定串阵营，重抓 |

所有榜单共用同一个批次号（`rank_probe.py --tag`），HTML 才能把多次抓包拼成一页；
单榜不达标只重跑该榜（最多 `--tries` 次），全流程结束后再生成
`rank_report_<tag>.html` 与 `rank_report_latest.html`。
