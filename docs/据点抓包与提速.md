# 据点抓包（tcpdump）与页面跳转提速

本文记录 2026-11-23 的两项改动与实测结论：

1. **不再用 OCR 扫表获取我方据点**：同盟建筑（同盟大营等）的坐标可以直接从
   tcpdump 抓到的游戏流量里解出来，单次约 **10s**，解码本身只要 **0.09s**；
2. **页面跳转/停留时间改为「就绪轮询」**：用截图像素指纹判定页面静止，
   替代原来的一堆固定 `time.sleep(2~3s)`。

---

## 1. 为什么 OCR 慢

用 [`tools/_flow_timing_summary.py`](../../tools/_flow_timing_summary.py) 汇总最近
63 轮自动拉线日志（`screenshots/flow/auto_line_*.jsonl`）：

| 节点 | 总耗时 | 每轮平均 | 占比 |
| --- | --- | --- | --- |
| 调动据点 | 27568.6s | 444.7s | 39.5% |
| 寻找敌方进攻 | 19531.3s | 443.9s | 28.0% |
| 回家补兵 | 12282.0s | 236.2s | 17.6% |
| 邮件分析战场 | 10382.3s | 164.8s | 14.9% |

其中重灾步骤：

| 步骤 | 次数 | 总耗时 | 平均 |
| --- | --- | --- | --- |
| 等待战斗结束 | 42 | 13992s | 333s |
| 回城就位 | 52 | 8423s | 162s |
| 选择歇兵城池 | 18 | 5168s | 287s |
| 定位最近可调动据点 | 52 | 4465s | 86s |
| 低兵部队进城歇兵 | 39 | 4014s | 103s |
| 战斗准备 | 44 | 3849s | 87s |
| 回城 | 42 | 3431s | 82s |

这些步骤里，「点一下 → 固定 sleep 2~3s → 整屏 OCR 判定」占了很大比例：
页面实际 0.3~1.2s 就切换完了，剩下的时间纯属白等。

## 2. 抓包能不能拿到「全部我方据点」——能（同盟建筑 100%）

### 2.1 结论

| 数据 | 能否从 pcap 拿到 | 说明 |
| --- | --- | --- |
| **同盟大营 / 同盟建筑** | ✅ 可以，100% | 打开「同盟」主页面时一次响应里带全部条目（名称 + 类型 + 坐标） |
| 同盟成员坐标 | ✅ 可以 | 同一响应里的成员数组，每条带主城坐标 |
| 城池列表（城/水寨/军港/民港） | ❌ 抓不到 | 实测打开「同盟 → 城池」并上下翻页都没有对应响应；客户端登录期缓存，仍走 OCR |

实测对照（同一时刻，竖屏 900x1600）：

```
抓包：同盟大营2(637,770) 同盟大营4(814,791) 同盟大营(700,809) 同盟大营3(838,780)
OCR ：同盟大营 (637,770) (700,809) (814,791) (838,780)   ← 完全一致
```

耗时对照：

```
抓包解码：0.09s（已有 pcap，纯解码）
抓包抓取：约 10~14s（起 tcpdump + 点开同盟页 + 停抓 + pull）
OCR 扫表：打开同盟建筑页 15.4s，含解析 32.2s；城池 14 屏全量扫描 2~5 分钟
```

### 2.2 流量格式（复用战报收录的解码链）

```
TCP payload
 └─ 2 字节大端帧长
     └─ 9 字节传输头
         └─ XOR(8 字节 key)        ← 每次抓包随机，需自动推导
             └─ 2 字节 RPC 前缀
                 └─ sproto-like 对象：u16 字段数 + u16 头表 + 长度前缀数据段
```

同盟建筑条目（实测两种布局，字段号不同但语义一致）：

```
item {
  tag0: 8 字节（未知）
  tag1: small = 5002        # 类型 id（5002 = 同盟大营，5020 = 器械/工事）
  tag2: u32  = 6370770      # 坐标：x*10000 + y  →  (637, 770)
  tag3: utf8 = "同盟大营2"   # 建筑名
  tag4: small = 1
  tag5: object              # 建筑详情（耐久/建造者等）
}
```

XOR key 不是固定的（本次抓到 `f3488db206d80000` / `ae0575dc3a340f00`，
历史战报抓包是 `3330d32fba040800`、`3740dd314ffe0a00`），
[`sanmou_auto/netcamps.py`](../netcamps.py) 用
`derive_xor_key_candidates` 出候选 + 「能否解成对象」打分自动挑选，不写死 key。

### 2.3 用法

```bash
# 只解析已有 pcap
python -m sanmou_auto.netcamps --pcap screenshots/flow/pcap/xxx.pcap

# 真机抓一次（需要 adb root + 设备内 tcpdump，实测 /system/bin/tcpdump）
python -m sanmou_auto.netcamps --capture --seconds 6

# 抓完直接写回据点缓存（保留缓存里已有的城池记录）
python -m sanmou_auto.netcamps --capture --sync
```

接到原子调度主链路（**默认关闭**，避免与战报收录抢 tcpdump）：

```bash
set SANMOU_NETCAMPS=1
python -m sanmou_auto.atomic_loop --minutes 10
```

命中条件：`commands/collect_camps` 发现「没有据点缓存」时，
先抓 6s 流量解出同盟建筑（约 10s）并写入 `camp_cache.json`，
再走沙盘快跳；失败自动回落到原来的 OCR 全量扫描。

探查工具：[`tools/pcap_probe.py`](../../tools/pcap_probe.py)

```bash
python tools/pcap_probe.py --flows   x.pcap     # 有哪些 TCP 流
python tools/pcap_probe.py --strings x.pcap     # 原始字节里的中文（确认数据在不在）
python tools/pcap_probe.py --packed  x.pcap     # 扫 x*10000+y 坐标
python tools/pcap_probe.py --tree    x.pcap --frame 7 --limit 200   # 结构树
python tools/pcap_probe.py --capture --cold --scrolls 3             # 冷启动抓取
```

## 3. 页面跳转提速：`sanmou_auto/fastwait.py`

思路：游戏内页面切换都是「静止 → 动画 → 静止」，用 32×18 灰度缩略图的帧间
差异就能判定，比整屏 OCR 便宜 1~2 个数量级（截图 ~0.25s，比对 <1ms）。

| 函数 | 用途 |
| --- | --- |
| `wait_settle(adb, box, timeout, min_wait)` | 等某个区域「动画结束并静止」 |
| `wait_until(adb, pred, timeout, interval)` | 轮询直到 `pred(img)` 为真（如「已回城」） |
| `tap_settle(adb, point, box, timeout)` | 点一下 + 等稳定，替代 `tap + sleep` |
| `wait_text(adb, box, keywords, timeout)` | 轮询区域 OCR 出现关键字；帧没变就跳过 OCR |

回退开关：`set SANMOU_FASTWAIT=0` 时退化成原来的固定 sleep。

### 已替换的固定等待

| 文件 | 位置 | 原等待 | 现在 |
| --- | --- | --- | --- |
| [`alliance.py`](../alliance.py) | 页签切换 `_open_tab` | 2.2s | 等目标区域静止（~0.6~1.0s） |
| alliance.py | 打开同盟主页/设施筛选 | 1.8~3.0s | `tap_settle` |
| alliance.py | 城池列表回顶/翻页 | 0.5s×5、0.9s/屏 | 等列表静止（0.12s 起） |
| alliance.py | 点坐标等跳转弹框 | 1.3s×3 | `wait_text` 轮询（~0.5s） |
| alliance.py | 确认跳转后校验按钮 | 2.2~3.0s + 0.3s | 等右侧按钮列静止 |
| [`mapnav.py`](../mapnav.py) | `ensure_map` | 每轮多一次面板 OCR | 先判地图，命中即返回 |
| mapnav.py | `confirm_jump` | 2.5s | 轮询弹框消失 |
| mapnav.py | `leave_city`（出城） | 2.5s | 等底栏静止 |

## 4. 新增：收集「我的主城」坐标（与城池不是一回事）

> **主城** = 自己的城（定位面板里第一条，名字是玩家名）；
> **城池** = 同盟「城池」页签里的城/水寨/军港/民港（那是据点）。
> 两者分开存：主城 → [`screenshots/flow/home_city.json`](../../screenshots/flow/home_city.json)，
> 据点 → `camp_cache.json`。

来源（实测）：点地图右上角「定位」箭头 → 页签 **建筑** → **列表第一条就是我的主城**
（行：`<玩家名>` + `<地块名>(x,y)`）。点开这一行后底栏会显示
`鄱阳-视田-乘风台(648,915) 整编(6)`，用其中的 `(x,y)` 校验 OCR 读到的数字。

```bash
python -m sanmou_auto.homecity                 # 读一次并打印
python -m sanmou_auto.homecity --verify        # 点开第一条，用底栏坐标校验
python -m sanmou_auto.homecity --verify --store  # 读 + 校验 + 落盘
```

模块：[`sanmou_auto/homecity.py`](../homecity.py)

- `HomeCity().collect(verify=True)` → `{"name","tile","coord","coordText","collectedAt"}`；
- `HomeCity().load_or_read(max_age=21600)` → 优先用缓存（迁城很罕见，默认 6h 重读）；
- `HomeCity().distance_to(coord)` → 主城到某格的距离。

自动拉线已接入：每轮开头用 `load_or_read` 取主城（缓存命中 0 成本），
日志打印 `== 我的主城：神卷路明非(648,915)`，结果 JSON 里带
`home_city` / `home_city_dist`（战场距主城格数）；`SANMOU_HOMECITY=0` 可关闭，
`SANMOU_HOMECITY_TTL=<秒>` 调缓存有效期。

顺带修掉一个地图判定 bug：城内视角底栏也是「武将/同盟/职业/证战」，
旧 `on_map()` 会误判成世界地图 → 现在先看左下按钮是「出城」还是「回城」。

## 5. 补兵（城池版）：离主城最近的城池 → 1-4 队全调动

这是用户要的补兵方式：不再「回城 → 亲卫营逐队点补兵」，而是

1. 取**我的主城**坐标（`homecity.py`）；
2. 在城池列表里挑**离主城最近**的城（优先「城」，其次水寨/军港/民港），
   自动跳过「无法入驻」这类点进去没有「调动」的城；
3. 用**沙盘坐标直跳**选中该城（不打开「同盟 → 城池」列表，那是 OCR 时代的慢路径），
   校验右侧出现「调动」；
4. 打开调动面板，把 **1-4 队**全部调动过去，城会按机制自动征兵；
5. 登记到 `screenshots/flow/city_rest.json`，`--status` 就是「补兵中的部队在哪」。

```bash
python -m sanmou_auto.city_replenish                # 选城 + 1-4 队全调动
python -m sanmou_auto.city_replenish --dry-run      # 只报告最近城池与距离
python -m sanmou_auto.city_replenish --troops 1,2   # 只送指定队伍
python -m sanmou_auto.city_replenish --status       # 正在城池补兵的部队
python -m sanmou_auto.city_replenish --recall       # 检查并召回已征满部队
```

原子调度的补兵固定走「城池补兵」（`commands/replenish_troops.py` →
`CityReplenish`），等价于老流程的 `--city-replenish`，替代「回城 → 亲卫营」：

```bash
python -m sanmou_auto.city_replenish --troops 1,2,3,4   # 单跑一次城池补兵
python -m sanmou_auto.atomic_loop --minutes 60           # 长跑（补兵自动进行）
```

实测（2026-11-24 00:38，主城 `(648,915)`）：

```
候选 城池 城641,923(641,923) 距主城 10.6
✓ 当前已选中 (641,923)，直接用
== 点击「调动」@(735, 709)
部队1 兵力 33000（达标）… 耗时 00:00:49 → 预计 00:39:08 到达
… 部队2/3/4 同理
✓ 已调动到城池补兵: 部队1, 部队2, 部队3, 部队4 @城641,923
```

### 5.1 顺带修掉的三个真 bug

| 现象 | 根因 | 修复 |
| --- | --- | --- |
| 「点不到调动按钮」 | 竖屏右侧按钮列整体左移，`ACTION_BOX` 只框到最右边，OCR 读不到「行军/调动/征兵」 | `config.ACTION_BOX` 竖屏改为 `(500,545,900,1000)` |
| 选中了也判「没有调动」 | 按钮文字 OCR 抖动：征兵→证兵、生产辎重→生产重、委任→委托、行军被气泡挡掉 | `has_mobilize_button` 放宽词表 + 按钮数 ≥3 兜底 |
| 卡在「地块详情浮层」出不来、连环弹「确认退出游戏」 | 详情浮层下 `ensure_map` 用小拖拽取消选中无效，反而连按 BACK | 每次 `ensure_map` 最多按 1 次 BACK；补「沙盘页识别 + 放大退出沙盘」（`SandboxJump.close()`）；`_select_city` 已选中同格时直接复用 |

另外 `_arrive_epoch` 修正：逐队登记时先派出的部队到达时间可能已过去，
直接 `% 86400` 会算成「明天同一时刻」，导致召回一直以为在途。

## 6. 已知边界

- 抓包需要 `adb root` 与设备内 `tcpdump`；没有 root 时 `--capture` 会直接返回空并
  由调用方回落 OCR（`SANMOU_NETCAMPS=1` 也只在有缓存缺失时才尝试）。
- 同一台模拟器同一时间只能跑一个自动化：战报收录 skill 与自动拉线互斥，tcpdump
  也只能有一份，所以该开关默认关闭。
- 城池列表（城/水寨/军港/民港）实测不在流量里，继续依赖 OCR/缓存；
  若后续发现新的 RPC（例如切换账号后首屏），可复用
  [`tools/pcap_probe.py --strings`](../../tools/pcap_probe.py) 继续定位。
